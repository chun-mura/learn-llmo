三層を混ぜない

技術面の話は、三つの層に分けてから読んでください。混ぜると、片方の層の失敗をもう片方の層の設定で直そうとすることになります。

1 届く→2 意味が付く→3 エージェントの地図

「届く」は Search と AI 出典の入場条件です。「意味が付く」はリッチリザルト用の手がかりです。「エージェントの地図」は llms.txt で、Search とは別系統です。三つは目的が違うので、たとえば「届く」で落ちているページに構造化データを足しても、出典としては拾われません。以降の節では、この順に一層ずつ見ます。

1. 届く

ここは一層目、「届く」の話です。Google の AI 機能に出典として出る条件は、通常 Search と同じで、インデックスされ、スニペット表示可能であることです。追加要件はありません。裏返すと、AI 面のために覚える特別な項目はなく、次の当たり前の前提が満たせているかどうかがすべてになります。

  • 検索ボットが robots.txt と WAF で止まっていない
  • 対象 URL が 200 で本文を返す
  • 重要情報が HTML テキストとして存在する
  • 内部リンクで辿れる

だから、この層で起きる不具合は、設定した内容と実際に配信されている内容のずれとして現れます。たとえば nosnippet などのプレビュー制御を付けたのに AI 面に本文が出る場合は、Googlebot が実際に取得した HTML にそのメタタグが含まれているかを、自分で確認してください。管理画面で設定した状態と、ボットに返っている HTML は別物です。

2. プレビューと構造化データ

ここからは二層目、「意味が付く」の話に入ります。ただしその前に、一層目を止めてしまうメタタグを区別しておきます。

  • noindex Search 全体から外す。AI 出典にも使えない
  • nosnippet 系 プレビューに出す量。厳しいほど AI 面も細くなる

二つの効き方は段違いです。noindex は「届く」ごと落とすので AI 出典の可能性も消えますが、nosnippet 系はインデックスは残したまま、見せる分量を絞ります。だから、AI 面の本文が細いという症状は、この二つのどちらが効いているかで対処が変わります。

そのうえで、二層目の構造化データです。これはページ内容の手がかりで、リッチリザルトの適格化に使います。推奨は JSON-LD で、マークアップは見える本文と一致させます。だから、空ページに JSON-LD だけ置くのは不可です。そして生成 AI 検索のために特別な schema は不要で、必須でもありません。つまり構造化データは、出典に選ばれるための条件ではなく、あくまでリッチリザルト側の仕事だということです。

3. llms.txt

最後が三層目、「エージェントの地図」です。llms.txt は Jeremy Howard の提案で、サイトの地図を Markdown で置きます。必須は H1 の名前で、詳細はリンク先の .md に置きます。書式は次のようなものです。

# Example Cloud Billing API

> 請求イベントを REST で送受信する。

## Docs
- [Authentication](https://example.com/docs/auth.html.md)

この層が前の二つと違うのは、そもそも Search の系統ではないところです。扱いが任意であることは監査ツールの挙動にも表れていて、Chrome Lighthouse の llms.txt 監査は、サーバーエラーのときは警告を出し、404 のときは N/A（任意）になります。つまり、置いていなくても Search 側の失敗にはなりません。

Google Search は llms.txt を使いません。ドキュメントをエージェントに案内する用途と、AI Overviews の出典選定は別です。
